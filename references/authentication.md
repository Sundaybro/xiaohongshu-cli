# 登录、二维码与浏览器

## 保存的凭证

先用 `xhs status --json` 判断会话有效性，不能仅以凭证文件存在判定登录成功。默认配置一般位于 `~/.xiaohongshu-cli/`，具体以安装版本为准；只引用路径，不展示或提交文件内容。

本分支 `cookies.py` 的 HERMES 补丁令 `extract_browser_cookies()` 直接返回 None，避免自动解密触发 macOS 钥匙串弹窗。它不影响已有凭证读取或浏览器扫码登录。不要反复执行普通 `xhs login` 来尝试自动提取；需要解密提取能力时，先说明该分支差异。

## 刷新登录

```bash
xhs login --qrcode
xhs status --json
```

正常流程由浏览器参与，终端显示二维码，用户在小红书 App 扫描并确认，CLI 保存凭证。扫码不等于已完成授权，必须等登录确认并复查 status。纯 HTTP 扫码此前曾遭遇 `type=124`，不要不断重试同一路径；优先检查浏览器参与的流程。

用户需要图片形式的二维码时，优先使用现有工具的导出能力；只有终端字符码时，可以从本次 QR 数据生成临时 PNG，保持同一有效会话。不要把二维码或其中的登录数据写入仓库。用户没有扫描成功或二维码过期时，结束旧流程后再生成，不同时运行多个会话。

登录成功后核对 `data.user.id` 与昵称。不同设备或 App 账号可能导致本次登录身份变化。确认本次目标账号后再继续账号相关写操作。

## 复用浏览器 profile

CLI 凭证与浏览器 profile 不自动同步。使用用户指定的已登录浏览器时，先探测实际可执行文件、profile 位置和是否已有进程。Firefox/Camoufox 的独立 profile 通常需要显式启动参数，例如：

```bash
"<browser-executable>" -profile "<private-profile-directory>" -no-remote "https://www.xiaohongshu.com/"
```

双击 App 可能使用默认 profile；同一 profile 不能同时被两个进程占用。保留用户现有窗口，优先复用，不直接复制整份登录目录进入项目。

浏览器界面操作使用当前环境支持的工具。原生窗口控制若需要系统权限，说明具体阻碍；授权或连接未完成时，不反复等待同一提示。内置浏览器是否支持导入登录态，必须以当前能力列表为准。

## 常见阻碍

| 状态 | 处理 |
|---|---|
| `not_authenticated` / 会话过期 | 浏览器扫码刷新，完成后复查身份 |
| `verification_required` | 用户在浏览器按提示完成验证，再继续 |
| `ip_blocked` | 停止请求，等待或由用户处理网络条件 |
| DNS、沙箱网络失败 | 按工具权限正常申请联网执行，不误报为登录失败 |
| 默认工作目录访问异常 | 使用一个可访问的工作目录运行只读 CLI，保留原项目文件 |

日志默认保持必要输出，避免以 verbose 模式输出原始请求、凭证或完整私信。
